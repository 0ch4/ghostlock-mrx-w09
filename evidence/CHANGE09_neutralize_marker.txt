ROOT CAUSE OF THE "SLOW ROOT" (why su was missing) [MEASURED]
  - `ghostlock_e --root` DID succeed.  Its realroot.txt (uid-0 child log) ends with:
        root: child POST uid=0 euid=0 suid=1 ctx='u:r:shell:s0'
        root: OWN CapEff=ffffffcfe0e0bd40 ...
        root: child proof attempted
        root: child entering su_server uid=0
    rooted.txt was written by uid 0.  So the root server \0gl_su WAS UP.
  - But /data/local/tmp/su (the CLIENT, a symlink to ghostlock_e) did NOT exist: the
    factory reset wiped /data/local/tmp and nothing recreates `su`.  So `su -c true`
    failed ("inaccessible or not found"), the restore script wrongly concluded
    "no root server", released the per-boot lock, and retried -> MULTIPLE concurrent
    exploit runs (load spike, watchdog/pid-0 panic risk).
  - FIX (applied in the FAST glboot.sh):
      * create /data/local/tmp/su -> ghostlock_e          (ROOTSHELL_MEMO 4)
      * detect root with the NAME-INDEPENDENT client mode
        `ghostlock_e --rshcli 'id -u'` == 0               (ROOTSHELL_MEMO 4)
    With this, root came up in ~10-25 s.
