## 4. 未解決のブロッカー（次セッションの主題）
1. **`--root-gms` の mount 失敗（0/3）の回帰**。
   - 症状: `gl.root.out` が空（`rm` で truncate されるため直近 run 分しか残らない）、`gl.klog` に詳細がある可能性、`ghostlock_e` が暴走。
   - 成功時（セッション前半）との差が出ていない。疑い: **freeze/permissive の取りこぼし**（P-14, `lr2` の freeze-retry は入っている）、**tmpfs base 非決定**（`glrt`/`glrt2`/`glrt3`/`/mnt`）、**staging 不良**。
   - ⇒ 方法: reboot → 1回だけ arm+trigger → **直後に `glroot.log`/`gl.root.out`/`gl.klog` をコピー退避** → mount エラー行（`root: gms overlays try=… priv=… errno=…`）を読む。
2. **Play が古い（同梱 15.2.67）**。以前は Play が自己更新して `/data/app` に **53.2.23-29**、GMS が **26.34.36** になって動いていた（`facts153b`）。**factory reset でその `/data/app` コピーが消え、同梱の古い版に戻った**。
   - 同梱 15.2.67 は UI で `java.lang.ClassCastException: com.google.android.finsky.stream.base.view.GridClusterPaddingView cannot be cast to adrl` を起こし **recovery mode に入って自己更新できない**（鶏卵）。

3. **YouTube 未インストール**。GSF は `/data/app` に居るので **いま定義は生きている** → この状態で YouTube を一度インストールすれば `READ_GSERVICES` が付与され永続。`/data/app` に YouTube が無いので `youtube_reinstall.sh` はまだ使えない。

## 5. 重要な知見（再発防止）
- **`su` symlink が無いと root 取得が「失敗」に見える**: `ghostlock_e --root` は成功し `\0gl_su` は上がるのに、`/data/local/tmp/su`（ghostlock_e への symlink）が無いと `su -c true` が失敗→スクリプトが「root 無し」と誤判定→ロック解放→**多重実行**。対策: `provision.sh` の `ln -sf ghostlock_e su`、検出は**名前非依存の `ghostlock_e --rshcli 'id -u'`==0**。
- **overlay の upper は tmpfs 必須**（`/data` upper は EINVAL）。**`/data` lower は可**。**merged root は最上位 lower のラベルを継承**。
- **EROFS 単一ブロック改変は dm-verity FEC に戻される** → 効かせるには FEC（同一 RS 群の2ブロック or parity）を壊す必要（今回は既に parity ゼロ化済みで marker が効いた）。**書き込み直後の `cat` はページキャッシュで古い**（`dd` 読み戻し sha で確認）。
- **`--root-gms` の overlay+`ctl.restart zygote` は PM を劣化させうる**（SAFETY）。Play 自己更新→`/data/app`→overlay 無しの次ブートで crash loop、が既知の破壊経路。
- 同一ブートで **exploit を2回走らせない／`inject_hook restore` しない**（リセット実測）。
- **canonical は失敗時にロックを解放**する設計なので、mount が失敗し続けると**暴走**する。失敗が続くときは手動で `ghostlock_e` を kill するか、ロック解放を止める。

## 7. 次の一手（優先順）
1. **掃除**: `pkill -9 ghostlock_e` → `adb reboot`。
2. **`--root-gms` 0/3 の原因特定**: クリーンな1回で arm+trigger 直後に `glroot.log`/`gl.root.out`/`gl.klog` を**退避コピー**し、mount エラー（`root: gms overlays try=… priv/perm/sys errno=…`）を読む。base 非決定なら実 base を確認。
3. **GMS 復元を成功させる**（overlay 3/3＋PRIVILEGED ×3）。
4. **Play/GMS を “動く版”に上げる**: Aurora を入れて（端末側で Play Protect 確認を許可）GMS/Phonesky を最新化 → 自己更新が回る状態に。
5. **YouTube を一度インストール**（GSF 定義下）→ `READ_GSERVICES` 付与 → 再生確認 → reboot 後も定義が残ることを確認。
6. （本丸）**SAFE boot-hook（P3）** を慎重に: `/data/gls` へ staging＋一度だけ chcon → `.rc`（post-fs-data, lower-only, upper 無し, boot 時 chcon 無し）→ **disarm 試験**（staging 退避→再起動→正常起動）。

## 8. 落とし穴・運用（要点）
- arm 直前に **`.glp0`/`.glp2`/`.glboot.*` を掃除**。hook が未武装の今なら安全。
- **perf が `-1` になる前に exploit を起動しない**（KASLR leak 失敗→120s 待ちで失敗）。
- **`/dev` はマーカーに使えない**（tmpfs 0755 root:root）。マーカーは `/data/local/tmp`。
- **tmpfs を `/dev`/`/mnt`/`/data/local/tmp` 本体に被せない**（`glrt*` の subdir のみ）。
- **overlay は all-or-nothing**（perm+sys 先、priv 最後、失敗時 umount ロールバック、3/3 でなければ framework 再起動しない）。
- **1回の arm で 1トリガ**。`inject_hook restore` は同一ブート禁止。
